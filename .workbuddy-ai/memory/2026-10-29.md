## 修复 `pnpm tunnel:ngrok` 打印错误公网链接

### 真实根因（两个叠加）

1. **ngrok 免费版禁止 HTTP 代理**（决定性原因）
   - 环境里有 `http_proxy` / `https_proxy` = `http://127.0.0.1:52527`（IDE 注入）
   - ngrok 继承后报 `ERROR: authentication failed: Running the agent with an http/s proxy is a Pay-as-you-go feature`
   - 新进程秒退 → 旧版脚本轮询 4040 抓到残留 ngrok 的旧 tunnel → 打印旧链接

2. **残留 ngrok 进程占 4040**
   - `killResiduals()` 后只 `sleep(500)`，Windows 释放端口 + 服务端注销 session 需要数秒
   - 旧版 `pollApi` 直接 `tunnels.find(x => x.proto === 'https')`，不校验 `config.addr`、不区分新旧 → 拿到过期链接

### 修复内容（scripts/tunnel.js，281 → 425 行）

| 新增 | 作用 |
|---|---|
| `envWithoutProxy()` | spawn 前剔除 `http_proxy`/`https_proxy`/`all_proxy`/`no_proxy` |
| `getNgrokTunnels()` | 读 4040 API，连不上返回 null（区分"无隧道"和"服务没起"） |
| `waitNgrokApiDown(8000)` | 杀残留后轮询等 4040 真正释放，替代 sleep(500) |
| `verifyPublicUrl()` | 打印前用 `ngrok-skip-browser-warning:1` 头请求 `/health`，校验含 `"ok"` |
| `displayWidth()` | CJK/emoji 按 2 列算，修中文行 `║` 边框错位 |
| `pollApi` 三重过滤 | 非 staleUrls + `addr` 匹配 PORT + 实际可达 |
| `checkHealth` 加强 | 要求响应体 `{"ok":true}`，防 9200 被别的服务占用时静默穿透错误后端 |
| stderr 分类提示 | 代理 / ERR_NGROK_334 / 认证失败 分别给人话提示 |

## 账号系统与玩家数据持久化

把原来的"输入昵称即玩"升级成完整账号体系。

### 新增文件

| 文件 | 作用 |

删除：`game-ddz-web/src/utils/user.ts`（昵称体系被账号体系取代，已无引用）

### 技术选型

**用 JSON 文件而不是 sqlite**：本地 Node 22.22 其实支持 `node:sqlite`，但根 `package.json` 的 `engines` 是 `>=18`，部署环境（Railway Nixpacks）未必是 22，用内置 sqlite 会有版本崩风险。JSON 零依赖、零版本门槛，备份就是拷一个文件，和"单进程 + 小规模玩家"的规模匹配。

**token 用无状态签名而不是 session 表**：HMAC-SHA256 签名，payload 含 `{pid, name, exp}`。好处是进程重启后 token 依然有效，玩家不用重新登录；代价是无法服务端主动吊销（本项目不需要）。

### 关键实现细节

- **数据目录定位**：编译后 `__dirname` 是 `dist/`，ts-node 直跑是包根，用 `path.basename(__dirname) === 'dist'` 判断后统一指向 `game-ddz-server/data/`，避免开发和生产各存一份。支持 `DDZ_DATA_DIR` 覆盖。
- **原子写**：`players.json.tmp` → `rename`，防半个文件；防抖 100ms 合并写入；`SIGINT`/`SIGTERM` 钩子 `flushNow()`。
- **损坏保护**：`JSON.parse` 失败先复制成 `.broken-<时间戳>` 再重建空库，不静默覆盖。
- **防冒充**：`onJoin` 校验 token 得到 `pid` → 查库得昵称 → 绑定 socket；消息入口把 `data.playerId` 强制覆盖成绑定值。改 URL 或改消息体都无法冒充。
- **登录失败统一提示**「昵称或密码错误」，不区分账号是否存在，避免被用来探测注册情况。
- **积分规则**：地主赢 +2 / 农民各 -1，农民赢地主 -2 / 农民各 +1；胜场仅赢家 +1，局数所有人 +1；`roomInfo.settled` 防重复结算。
- **顺手修掉**：`/api/createRoom` 现在也校验 token，已登录时以 token 昵称为准。

### 顺手修掉的 UI 问题

- 全局主题色从 antd 默认蓝改成绿色 `#52a83f`（`ConfigProvider theme`），按钮/Tab/链接统一

## 修复：第三个人能中途加进来重开 / 只有房主能增删 AI

### 问题现象

两个真人 + 一个 AI 正在打，第三个人点链接进来，房间直接被重置成准备阶段，牌局没了。

### 三个叠加成因（缺一不可）

1. `onJoin` 里无条件 `roomInfo.status = 'prepare'` —— 任何人进来都把局冲掉
2. `socket.on('close')` 直接调 `onLeave` —— 刷新一次页面就腾出座位，等于给人开门
3. `onAddAI` 里原本有一行注释 `// 允许任何玩家添加 AI（不限房主），方便空房间/测试` —— 谁都能塞 AI，塞满 3 人触发自动开局

### 修复方案

- **房主模型**：`RoomInfo.ownerName` = 第一个进房间的真人。房主离开时 `transferOwner()` 顺位交给下一个真人；真人全走光房间销毁。
- **入房拦截**：`status !== 'prepare'` 直接返回 `isGameInProgress: true`，前端弹 `Modal.warning` 引导回大厅，房间状态一点不动。
- **断线宽限**：`socket.on('close')` 改成 `markOffline()`，只把 `isOnline` 置 false 并挂 90s 计时器（`disconnectTimers`，key 为 `roomId:playerId`）；超时才真正 `removePlayer()`。重连时清计时器、恢复 `isOnline`。
- **AI 增删权限**：`onAddAI` / `onRemoveAI` 开头判 `isOwner()`，非房主返回 `'只有房主可以添加 AI'`；`onRemoveAI` 额外要求准备阶段 + 目标确实是 AI（不能踢真人）。`onStart` 加 `internal` 参数，AI 满员自动开局时跳过房主校验。
- **离线托管**：`scheduleAITurn` 的条件从 `!current.isAI` 改成 `if (!current.isAI && current.isOnline) return;` —— 掉线玩家的回合由 AI 代打，不会卡死牌桌。

### 前端

- 准备阶段的按钮区按 `amOwner` 分支：房主看到「添加 AI / 开始游戏」，非房主看到「等待房主 xxx 开局…」
- AI 头像右上角加红色 `×` 移除按钮（`PlayerHeader` 新增可选 `onRemove` prop，`avatarSlot` 定位），只在房主 + 准备阶段 + 目标是 AI 时渲染
- 收到 `gameInProgress` 消息 → `Modal.warning` + 跳回 `/room`

### 验证

- 后端脚本 17 项断言全过：中途第三人加入被拒且房间状态不变、非房主 addAI/removeAI 被拒、房主 addAI 成功、房主不能移除真人、房主 removeAI 成功、断线保座 + 重连恢复、房主离开转移房主
- UI 实测：房主 1 个移除按钮 / 1 个开始按钮 / 1 个添加按钮；访客 0 / 0 / 0 且显示等待提示；点 × 后 AI 消失
- 写测试脚本时踩坑：房间广播会连发多条，`ws.next()` 容易拿到上一条旧广播 → 加了 `waitFor(pred)` 循环匹配，才从 13 过 4 挂变成 17 全过

## 修复：选中牌点不到旁边 / 出牌区堆叠被裁切

### 问题 1：牌排太近，选中一张后点不到旁边那张

**根因不是"排太近"，是点击热区和层叠顺序打架。**

叠牌时每张牌被后一张盖住右边一大截（原来重叠 58%）。牌面本身 `pointer-events` 默认 auto，
整张牌都在接点击；而选中牌被 `z-index: 999` 提到最上层 —— 于是它把**旁边那张牌露出来的点数区一起盖住了**。
用户看到的是"露出 42% 的点数"，点下去命中的却是上面那张选中牌（表现为取消选中/没反应）。

算一下就明白：牌宽 W、重叠 -0.58W 时，第 i+1 张的露出区是 `[x_i+0.42W, x_i+0.84W]`，
完全落在第 i 张牌盒 `[x_i, x_i+W]` 里面 —— 只要第 i 张置顶，第 i+1 张的露出区必然被挡死。

**修法（纯 CSS，不做坐标计算）：**

```less
.cardBox { pointer-events: none; }
.cardHit {                       // 只覆盖自己露出的那一条
  position: absolute; inset: 0 auto 0 0;
  width: calc(var(--card-w) + var(--card-gap));   // gap 为负 → 露出宽度
  pointer-events: auto;
}
.cardBox:last-child > .cardHit { width: var(--card-w); }  // 最后一张整张可点
```

- 相邻热区严格不重叠 → 点哪儿选哪张，跟 z-index 无关
- 选中牌只有自己那条热区接点击，右侧区域对鼠标透明 → 点击穿透到下面那张
- 顺带把重叠从 58% 收到 46%（露出 54%），热区从 29px 变成 41px，更好点
- 手机断点 62% → 52%

**两个坑：**

1. 热区宽度一开始写 `100% + var(--card-gap)`，实测每张比步长少 2px（`100%` 是 padding box，
   已扣掉两侧 1px 边框），逐张累积出 2px 的点击缝隙。改用 `var(--card-w)` 精确等于步长。
2. 按压缩放 `&:active` 失效（牌 pointer-events: none 命中不到），改用 `:has(> .cardHit:active)`
   反而把 `.active` 的抬起位移覆盖掉了（特异性更高），按下时牌会往回掉一下 —— 直接删掉这个效果。

### 问题 2：出牌区堆太多，最底下那张不完整且没对齐

`data.round` 是整局累积的出牌历史，早前 `flex-direction: column` 整列渲染 + `max-height: 46%` + `overflow-y: auto`
→ 局一长就堆到十几行，超出的被裁掉（最底下那张只剩半截）；每行前面的昵称长短不一，
牌行起点参差不齐，所以看着"没对齐"。

**修法：只渲染最后一手。**

- `const lastRound = roundCard[roundCard.length - 1]`
- 昵称单独一行居中（`.roundCardUser`），牌行从同一起点排
- 牌之间重叠 34%（`margin-right: calc(var(--card-w) * -0.34)`），20 张也不溢出；手机 10 张只占 166px
- 去掉 `overflow-y` / `max-height`，不存在裁切
- 容器 `pointer-events: none`，不挡「瞄准道具点空白取消」
- 昵称颜色从白改成深棕 `rgba(88,56,18,.85)` + 白色高光 —— 米色桌面上白字太淡

**为什么只渲染最后一条是对的**：服务端 `onNotUseCard` 在两家都"不要"后会 `roomInfo.round = []`，
所以最后一条天然就是当前有效的那手牌；`roundCard.length === 0` 正好是"新一轮起手"，
此时显示中央回合提示条，两者互斥不会重叠（我一开始以为会重叠，把提示条挪到 `bottom: 9%`，
看了代码才发现条件互斥，已改回原位）。

### 顺带

`--card-w` 的 vw 系数 9.2 → 8.2。露出量提高后每张牌更宽，20 张在 768px 平板上会顶出容器
（768×8.2% = 63px，20 张 = 709px < 752px 可用宽度）。

### 验证

- 热区宽度 = 步长：桌面 41 / 41，手机 16 / 16，无缝隙
- 点第 2 张 → 只有它抬起；**保持选中再点第 3 张 → 两张都选上**（说明点得到旁边的牌）
- 出牌区 `rowCount: 1`，`clipped: false`，`overflowY: visible`；10 张一手在手机上 166px 不溢出
- 1280×800 / 390×844 截图确认，无 console 错误

## 修复：出牌时背景抖一下

### 现象

点「出牌」的瞬间，牌桌背景（椭圆 + 水印）会往下抖几像素，像画面重新排版了一次。

### 根因：底部按钮区高度塌了 6px

`.btnBox` 是条件渲染的 —— 轮到自己才出现「不要 / 出牌 / 取消」，轮到别人时整个 `Space` 消失。
它原来只写了 `min-height: 46px`，而按钮实际是 40px 高 + 上下 padding 12px = **52px**。

于是按钮一消失，`.btnBox` 就从 52 掉到 46。`.table` 是 `flex: 1 1 auto`，会把这 6px 全吃掉：
牌桌椭圆高度 569 → 575，水印 top 147 → 148。视觉上就是"背景抖一下"。

逐帧采样实测（rAF 采样 240 帧）：

```
帧 4: [569, 191, 52, 800] → [575, 185, 46, 800]
      tableSurface myContent btnBox docScroll
```

### 修法

`min-height` 直接等于「按钮高 + 上下 padding」：

| 场景 | 按钮高 | padding | min-height |
|---|---|---|---|
| 默认 | 40px | 12px | 52px（原 46） |
| max-width: 480px | 38px | 12px | 50px（原继承 46） |
| max-height: 620px | 34px | 6px | 40px（本来就对） |

以后调按钮高度要同步改这个值。

### 验证

三个视口（1280×800 / 390×844 / 780×400）逐帧采样 240 帧，`tableSurface` / `myContent` / `btnBox`
**全部零变化**；再手动把 `btnBox` 的 innerHTML 清空模拟"按钮消失"，高度依旧 52 / 50 / 40 不变。

顺带确认：`doc.scrollHeight === clientHeight`、`innerWidth - clientWidth === 0`，
没有滚动条出现，所以不是滚动条引起的宽度变化。

## 修复：H5 手机首屏空屏 + 登录页加载很久

### 现象

手机第一次打开，先看到一大片纯色空屏（用户形容"大黄屏"），过了很久才出现登录页。

### 实测（iPhone 13 视口 + 1.5Mbps + 150ms 延迟 + 4 倍 CPU 降速）

改造前逐秒采样：**t=500ms ~ 6000ms 期间 `#root` 是空的**，什么都没有，7 秒才出登录页。
本地渲染出来是绿色（`rgb(63,139,54)`），**没能复现出黄色** —— 用户看到的黄屏
大概率是穿透服务商的浏览器提示页（ngrok 免费版那层），不是我们的页面。

### 四个真实原因

1. **没有 gzip**。`express.static` 直接发原文件，`index.js` 990KB 一个包，手机上就是硬下 990KB。
2. **没有骨架**。`index.html` 里只有一个空的 `<div id="root">`，JS 没跑完之前屏幕上一片纯色。
3. **单包不拆**。antd + react + 业务代码全塞在 `index.js` 里，改一行代码用户就要重下全部。
4. **`Cache-Control: max-age=0`**。带 hash 的资源每次都要回源验证。

### 改法

**服务端（app.ts）**
- 加 `compression` 中间件，**必须放在 `express.static` 之前**；filter 里排掉 `image|audio|video`（mp3/图片本来就是压缩格式）
- `express.static` 加 `setHeaders`：`/assets/*` → `immutable` 一年；`index.html` → `no-cache`；其余 1 天
- SPA fallback 的 `sendFile` 也补 `no-cache`

**前端**
- `index.html` 内联骨架：`<style>` + `#splash`（四花色 + 标题 + 转圈），零外部依赖
- **骨架必须挂在 `#root` 外面**：首帧路由是 `/ → /room → /login` 两次 `<Navigate>`，中间渲染 `null`，
  骨架放里面会被 React 清空 → 闪一下又空屏。改用 `#root:not(:empty) ~ #splash { display:none }`
- `router.tsx` 三个页面全改 `React.lazy`；`App.tsx` 包 `<Suspense fallback={<PageLoading/>}>`
- 新增 `components/pageLoading/`，视觉和 index.html 骨架一致，切换无缝
- `vite.config.ts` 加 `manualChunks`：react / antd / vendor 三块独立
- 大厅的 `moment(item.roomId).format(...)` 换成 5 行原生 `Date`，顺手从依赖里删掉 moment + 那个没用的 `ant-design@1.0.0`

### 结果

| 指标 | 改造前 | 改造后 |
|---|---|---|
| 首帧可见 | 7s（期间全空） | **300ms 出骨架** |
| 登录页可交互 | ~7s | **~1.5s** |
| 入口 JS | 990KB 单包 | 8KB（其余并行 modulepreload） |
| 传输量 | 990KB 未压缩 | ~290KB gzip |

### 顺带修的构建脚本问题

`pnpm build` 在 Step 3 崩了：`SAFE_DELETE_BULK_CONFIRM_REQUIRED`。
原因是 build.js 用 `rmSync(dir,{recursive:true})` 先清空再复制，Step 2 删 29 项 + Step 3 删 27 项，
累计超过宿主的单轮批量删除阈值（50）。分包后 chunk 变多，正好顶破。
改成 `syncDir()` 镜像同步：逐文件覆盖 + 只清理 src 里已不存在的条目，正常构建删除动作接近 0。

### 遗留可选优化

登录页 290KB 里 249KB 是 antd。想再快一档就得把登录页的 antd 摘掉（手写表单 + 把
`ConfigProvider` 从 `main.tsx` 挪到非登录页的外壳里）。改动面不小，暂未做。

## 修复：左右两张都选中时，中间那张牌被盖住点不到

### 现象

手牌里选中 A 和 C 两张（B 在中间），B 就被两边遮住，看不清点数也点不准。

### 根因：`.active { z-index: 999 }`

叠牌靠的是「后渲染的盖住前一张的右半截」——每张牌只露出左边一条（`--card-w + --card-gap`，约 54% 牌宽）。

选中态为了「让选中的牌完整可见」加了 `z-index: 999 !important`，后果是**整张牌身（100% 牌宽）浮到最上层**，
把右边那张牌的露出区盖掉一大截。

实测（1280 宽，牌宽 76px，露出区 41px）：

| 指标 | 数值 |
|---|---|
| 中间牌热区 | x=371，宽 25px（960 宽视口） |
| 左邻居（选中）牌身 | x=345，宽 46px → 覆盖到 391 |
| **中间牌实际可见宽度** | **5px / 25px（80% 被盖）** |

热区本身没重叠，所以 `elementFromPoint` 测出来还是中间牌自己——**功能上点得到，视觉上找不到**。
这也是为什么之前那版「热区」修复没覆盖到这个问题：热区解决「点得到」，不解决「看得见」。

### 修法

删掉 `.active` 的 `z-index: 999 !important`，选中态只保留：

```less
.active {
  transform: translateY(calc(var(--card-w) * -0.26));
  box-shadow: 0 6px 14px rgba(0,0,0,.28), 0 0 0 2px #ffd43b;
  /* 不写 z-index */
}
```

层叠顺序 100% 交给 DOM：后渲染的永远盖住前一张的右半截，每张牌的露出区都完整可见。

副作用（可接受）：选中牌黄色描边的右半边会被下一张牌切掉。真实扇形手牌也是这样——选中牌是塞在下一张底下的。

### 验证

1. **像素级**：关掉所有 `box-shadow`（否则抬起牌的投影会渗进比对区域，分不清「被阴影染色」和「被牌身遮挡」），
   对比中间牌点数区在「没选中」和「左右都选中」两张截图 —— **md5 完全一致**，证明没被遮挡。
2. **交互**：点中间那张 → 三张全部选上（`[5,6,7]`）。
3. **多视口回归**：1280 / 1100 / 960 / 820 / 700 / 560 / 480 / 390 全部通过，
   包括「尾部三张」（最后一张热区是整张宽，容易踩坑）。

### 教训

「热区不重叠」只能保证点击命中的正确性，**不能保证视觉可见**。
凡是给叠牌加层叠提升，都要先想清楚它会不会盖掉邻居的露出区。
